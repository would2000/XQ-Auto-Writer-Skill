# 選股、警示與自動交易的回測設定契約

本契約只適用於使用者明確要求執行歷史回測時。回測成功、交易筆數、報酬或任何績效數字，只是 XQ 在指定資料、商品、期間與設定下的客觀輸出；不得據此宣稱策略可行、獲利、穩健或適合實際交易。

## 共通規則

任何回測設定或商品選擇輸入之前，先依操作憲法第八條取得同一腳本名稱、類型及來源版本的當次真實 XQ 編譯 `success`。XScript 標題含「未編譯」、只完成設定 dry-run，或只能讀回名稱與 `自訂/CODEX/` 位置時都必須停止；先修正真實編譯錯誤，成功後才能開啟回測環境。

### 可預設，但必須告知使用者可調整

- 初始資金與成本模型可使用工具預設值，但回測前後都要列出實際採用的數字、費率與滑價／成交假設（若 XQ 有提供）。
- 日線或更高頻率預設每日最多進場一次。
- 分鐘頻率預設每次訊號只進場一次；開始前要提示使用者可改為分批進出場，但不得自行假定有加碼、減碼或多筆委託需求。
- 股票未指定商品範圍時，可先提議「上市櫃普通股」作為候選預設範圍；回測前仍須將實際宇宙讀回並告知使用者。
- 可提議最近六個月作為預設回測長度，以避免執行時間過長；不得把提議直接當成已授權的日期區間。

### 必須由使用者明確定義或確認

- 腳本／回測頻率。
- 停損與停利規則及其單位；若適用，也要定義觸發價格、成交價格與同一根 K 棒觸及多個條件時的處理方式。
- 執行商品類型與範圍：台指期、小台指、微型台指、個股或其他商品；期貨另須指定日盤或全日盤（日盤加夜盤）。
- 回測起訖日期。代理可提議六個月，但必須取得使用者明確確認才可執行。
- 若為分鐘 K，未觸及停利／停損時是否在收盤前強制平倉。
- 若使用者要求分批進出、加減碼、隔夜部位、轉倉或非預設成本模型，需明確定義其規則後才能宣稱回測設定完整。

## 選股腳本（screener）

市場別與商品範圍的實測工作流另見 [screener-backtest-product-guide.md](screener-backtest-product-guide.md)：預設必須讀回，其他範圍則交由使用者選取，並在開始前取得停利、停損與最大持有期（交易日／天數）的明確設定。

- 選股回測僅可使用日線或更高層級頻率；遇到分鐘頻率需求，應說明此類型不適用並改建議警示或自動交易。
- 選股腳本只負責選出標的，沒有腳本內的進出場與部位管理。若執行選股回測，持有期間、換股／再平衡、出場規則、最大持股數與資金配置都必須由使用者在回測設定中明確定義。
- 可預設每日選股一次；使用者可改為較低頻的再平衡。不得把選股條件命中視為已成交或策略可行。

## 警示腳本（alert）

- 警示回測可使用日線與分鐘頻率。腳本負責觸發進場訊號；出場、停利、停損與持有規則由回測設定決定，不能假裝已由腳本控制。
- 因此工作流應將警示腳本定位為適合半自動交易／訊號下單情境，而非完整的腳本內交易管理；不得啟用帳號、下單模組或實單功能。
- 分鐘頻率須先取得使用者對分批進出與收盤前強制平倉的明確選擇。

## 自動交易腳本（autotrade）

- 自動交易腳本可在腳本內定義進出場、部位與風險控制，並可用於期貨與股票商品；仍僅能在使用者明確授權的歷史回測或內建模擬範圍中操作。
- 腳本設計前必須取得頻率、停利、停損、商品／盤別、最大部位與分批進出需求。分鐘頻率另須取得收盤前平倉選擇。
- 回測時要同時讀回腳本內風控與 XQ 回測視窗的安全限制。兩者不一致時，應回報差異，不得自行選擇較寬鬆的限制。

## 共用商品範圍驗證契約

選股、警示與自動交易的回測介面並非假定為同一套控制項；三者共用的是可讀回的範圍安全契約。

- 警示與自動交易使用公開商品逐檔清單：先只記錄是否原有選取，再清空、讀回空清單、以精確名稱加入每一商品，最後讀回精確最終集合。
- 選股只可使用系統預設範圍或使用者自選股組合：系統範圍須先設定並讀回市場、重新讀取範圍，再設定並讀回名稱以 `(系統)` 結尾的完整名稱；自選組合只能由使用者手動選定，CODEX 不讀取或變更其名稱與內容。
- 不會讀取、使用或刪除私人自選／群組；任何不唯一的商品、沒有清空讀回、範圍讀回不符或控制項不明，都應停止。
- 結果一律輸出 `scope_selection` 證據：selection mode、requested 公開範圍、清空與最終驗證狀態、以及 `private_source_touched: false`。不適用清單清空的系統範圍欄位應為 `null`；自選組合則必須揭露由使用者手動選取且名稱未保留，不能偽稱 CODEX 已做精確最終驗證。

目前警示、選股與自動交易 scope-only 轉接器只提供 `--dry-run` 設定驗證：驗證完成後會取消視窗，不會啟動回測、產生報告或改動 checkpoint。三者也必須先通過唯讀 `recovery-status`；既有 `manual_review_required` 時不得開始。每次實體輸入前必須讀回精確目標 handle 已位於 Windows 前景；前景驗證失敗或發生等待事件後不得補送取消或自動重試。

警示完整回測另由 `xq_alert_backtest_run.py` 執行，而且腳本名稱與每個「必須明確定義」欄位都要以 CLI 參數傳入；工具必須先唯讀驗證該名稱、警示類型及 `自訂/CODEX/` 位置。非 dry-run 還必須加入 `--confirm-historical-backtest`。開始前 checkpoint 保存可見報告 handle 基準；Start 只送出一次，設定視窗晚關閉時只做唯讀監控，不得密集點擊。狀態依序保存 `starting`、`running`、`late_report`、`completed`，並能辨識隱藏進度窗與有界晚到報告。結果只有在唯一新增報告 handle、標題中的指定腳本 marker 及可解析摘要全部吻合時才可關聯；完整報告取得後只清理該新增報告。無結論 timeout、報告不唯一、marker 不符或證據不足時保留 checkpoint 並維持 `manual_review_required`，不得把既有或任意新報告當成結果。

正常完成的三類回測共用 `xq_backtest_monitor.py`，設定轉接器仍依選股、警示及自動交易各自的控制項與商品範圍契約實作。共用只代表啟動、監控、報告關聯與清理規則一致，不代表三種設定頁控制項相同。任何尚未實機讀回的選股欄位都必須先校正，不得套用警示或自動交易的 control ID 猜測。

## 人工復原確認

`manual_review_required` 或 `safe_to_clear_checkpoint` 都不是自動清除授權。使用者已在 XQ 人工確認指定工作確實結束後，才可使用：

```powershell
python .agents/skills/xq-xscript-compiler/scripts/xq_recovery_acknowledge.py --config .xq-auto-writer/xq-ui.json --run-id <recovery-status 的精確 run ID> --confirm-manual-recovery
```

工具不開啟設定或回測視窗；它會重新讀回 checkpoint、XQ／XScript 健康、可見進度與決策，要求 run ID 完全相同、沒有可見進度且檢查完整。`manual_review_required` 仍要求 XQ 與 XScript 健康；`safe_to_clear_checkpoint` 若已證明舊 PID 結束，則允許 XScript 尚未重開，但必須另有不同的正數 XQ PID、健康的主視窗及完整的舊行程已結束原因碼。成功時先建立私有且不可覆寫的封存紀錄，再驗證 checkpoint 未改變後清除。封存僅含 checkpoint 識別與狀態、雜湊及人工確認時間，不含商品、腳本、帳號、參數或報告績效。既有 `--acknowledge-stale-checkpoint` 不再具備清除能力。

## 回報格式

回報必須區分：

1. 腳本產生與編譯是否成功。
2. XQ 是否正常套用商品、頻率、日期、成本與風控設定。
3. 回測是否完成、成功／失敗商品數與 XQ 報告的客觀欄位。

不得從以上任何結果推論未來績效、投資建議、策略有效性或實盤安全性。
